==============================
Lab1 util + syscall 实验报告
==============================

一、实验目的

本实验旨在熟悉 xv6 操作系统中的系统调用机制，
理解用户态程序与内核态程序之间的交互方式，
掌握 UNIX 风格的进程创建、进程通信以及系统调用的扩展方法。

通过实现 sleep、pingpong、trace 和 sysinfo 等功能，
加深对操作系统内部工作原理的理解。

------------------------------------------------

二、实验环境

本实验并未完全按照实验指导中推荐的 Ubuntu 20.04 环境进行，
而是在 VMware 虚拟机中安装的 Ubuntu 24.04.3 LTS 环境下完成。

具体实验环境如下：

- 主机开发方式：VSCode Remote SSH 远程连接虚拟机
- 虚拟化平台：VMware
- 虚拟机系统：Ubuntu 24.04.3 LTS
- 系统代号：noble
- Linux 内核版本：6.14.0-29-generic
- 机器架构：x86_64
- QEMU 版本：8.2.2
- xv6 运行方式：QEMU 模拟 riscv64 平台

在实际开发中，我没有直接在 VMware 图形界面中完成全部代码编写，
而是使用 VSCode 通过 SSH 远程连接到虚拟机进行开发。
这样做的主要原因是：虚拟机自身的图形界面显示清晰度较低，

更方便的代码搜索与跳转功能，同时仍然能够在虚拟机终端中完成编译、运行和测试。

这种开发方式兼顾了实验环境的一致性与代码编辑效率，
使我能够更方便地阅读 xv6 的用户态与内核态源码，
并通过远程终端执行 make qemu、make grade 等命令完成实验验证。

三、Task1：sleep 程序实现

在用户态中，需要从命令行参数中读取用户输入的睡眠时间，
由于命令行参数默认以字符串形式传递，因此需要使用 atoi 将其转换为整数，
随后调用 xv6 已经提供的 sleep 系统调用，并在程序结束时调用 exit(0)。
其中，用户态程序中的 sleep(n) 并不是真正的睡眠逻辑实现，
而是通过系统调用机制进入内核，由内核中的 sys_sleep() 完成实际的进程阻塞与调度控制。

Q：为什么在 xv6 中执行 sleep 10 时，程序暂停时间远小于 10 秒？

A：这是因为 sleep 系统调用的参数单位并不是现实时间中的秒，
而是 xv6 内核中的 tick。
tick 表示两次时钟中断之间的时间间隔，
系统每发生一次时钟中断就会将全局变量 ticks 增加 1。
因此，sleep 10 实际表示让进程等待 10 个 tick，
而不是等待 10 秒。

四、Task2：pingpong 进程通信

在实现过程中，需要首先创建两个 pipe，
分别用于父进程向子进程发送数据以及子进程向父进程发送数据。
由于 pipe 是单向通信机制，其返回的文件描述符数组中，
fd[0] 表示读端（read end），fd[1] 表示写端（write end），
数据只能从写端流向读端，因此无法通过单个 pipe 实现双向通信。

在调用 fork 创建子进程后，父子进程会继承相同的文件描述符表，
从而共享同一个内核中的 pipe 对象。
父进程首先通过 write(pipe1[1], &buf, 1) 向 pipe 写入数据，
子进程随后通过 read(pipe1[0], &buf, 1) 从内核缓冲区中读取数据。
子进程完成打印后，再通过第二个 pipe 将数据写回父进程，
父进程最终从对应读端读取数据并输出结果。

在通信过程中，pipe 提供了阻塞语义（blocking semantics）。
当读端调用 read 时，如果 pipe 缓冲区为空，
内核不会立即返回错误，而是将当前进程挂起，
等待其他进程向该 pipe 写入数据后再唤醒，从而实现隐式的进程同步。

Q：为什么要创建两个通道，每个通道又有两个接口？

A：pipe 本质上是一种单向通信机制。
在调用 pipe(fd) 后，操作系统会返回两个文件描述符，
其中 fd[0] 为读端（read end），fd[1] 为写端（write end），
数据只能从写端流向读端。
由于 pingpong 程序需要实现父进程向子进程发送数据，
以及子进程再向父进程发送数据，
因此需要建立两个 pipe 来分别表示两个数据流方向：
第一个 pipe 用于 parent → child，
第二个 pipe 用于 child → parent。
每个 pipe 提供两个接口，是因为操作系统需要明确区分读权限与写权限，
从而保证数据流方向的确定性，
避免多个进程在同一通道中同时读写导致数据混乱或同步错误。

Q:为什么开始就要关掉通道的其中一端呢？

A：在 fork 之后，父进程和子进程会继承完全相同的文件描述符表，
因此两个进程都会同时持有 pipe 的读端和写端。
如果不关闭不需要使用的一端，
内核会认为该 pipe 仍然存在潜在的数据写入者，
从而导致读操作无法正确判断通信是否结束。
例如，当读端调用 read 时，如果仍然存在未关闭的写端，
即使当前缓冲区为空，内核也不会返回 EOF，
而是继续阻塞等待新的数据写入。


Q:如果先运行子进程的话，read函数应该先调用,为什么不会出错而是正常运行呢？

A：这是因为 pipe 的 read 操作具有阻塞语义。
当子进程在 pipe 缓冲区为空时调用 read，
内核不会立即返回错误，而是将该进程挂起，
并将其加入等待该 pipe 数据的等待队列中。
当父进程随后调用 write 向 pipe 写入数据时，
内核会唤醒等待在该 pipe 上的进程，
使子进程重新进入可运行状态并继续完成 read 操作。

Q:不同的父子进程关掉不同的通道不会有影响吗？还是每个进程保持不同的数据呢？

A：不会产生冲突，因为文件描述符表是进程私有的数据结构。
虽然 fork 后父子进程最初指向同一个内核 pipe 对象，
但每个进程对文件描述符的关闭操作仅影响自身的文件描述符表，
不会直接删除内核中的 pipe。
只有当所有指向某个 pipe 写端的文件描述符都被关闭时，
内核才会认为该 pipe 不再可能被写入数据，
此时读端调用 read 才会返回 EOF。

五、Task3：trace 系统调用追踪

在 xv6 中，所有用户态系统调用都会通过 ecall 指令进入内核，
并统一在 syscall() 函数中进行分发。
因此，只需在 syscall() 中根据当前进程的 trace_mask 判断
是否需要打印调试信息，即可实现对所有系统调用的统一追踪。
在进程控制块结构 proc 中新增一个成员变量 trace_mask，
用于记录当前进程的追踪配置。
在 sys_trace() 的实现中，通过 argint 获取用户传入的 mask，
并将其存入当前进程的 trace_mask 字段中，从而实现追踪开关的设置。
为了保证追踪行为在进程创建后仍然有效，
需要在 fork() 实现中将父进程的 trace_mask 复制给子进程，
使子进程继承相同的系统调用追踪策略。
最后，在 syscall() 函数中，
根据位运算判断该系统调用编号是否在 trace_mask 中被置位。
若条件满足，则调用 printf 输出调试信息。

Q: trace_mask是什么，储存着什么让它为什么要从父进程传递给子进程

A: trace_mask 是存储在进程控制块（proc）中的一个整数变量，
用于表示当前进程需要追踪的系统调用集合。

Q：为什么 trace_mask 要存储在 proc 结构中，而不是使用全局变量？

A: 在调用 trace(mask) 系统调用后，
当前进程的 trace_mask 会被设置为对应值，
从而影响后续系统调用执行时是否打印调试信息。
在 fork 创建子进程时，需要将父进程的 trace_mask 复制给子进程，
子进程通常被视为父进程执行环境的延续。
如果不继承 trace_mask，
则可能出现父进程开启了追踪，而子进程未开启追踪的情况

Q：为什么 trace_mask 要存储在 proc 结构中，而不是使用全局变量？

A: 如果使用全局变量来保存 trace 配置，
则所有进程将共享同一追踪策略，
无法实现针对单个进程的精细控制。

Q: int r = syscalls[num]();是什么？

A：从系统调用函数指针表 syscalls 中取出对应的内核处理函数，
并执行该函数。
通过 syscalls[num]() 的方式，
内核可以根据用户程序通过 ecall 传入的系统调用编号，
动态调用对应的处理函数，
实现系统调用的统一分发机制。
变量 r 用于保存该系统调用执行后的返回值，
后续在 trace 功能中，
内核会根据 trace_mask 判断是否需要打印该返回值，
从而实现系统调用执行结果的追踪与记录。

Q：为什么 trace 的打印逻辑要放在 syscall() 中，而不是放在每一个 sys_xxx() 函数内部？

A：syscall() 是所有系统调用的统一分发入口。
如果在每个 sys_xxx() 内部添加打印逻辑，
不仅会造成代码重复，
也会增加系统维护成本。

六、Task4：sysinfo 系统状态统计

在 sys_sysinfo() 的实现中，
首先通过 argaddr 获取用户传入的虚拟地址，
然后分别调用辅助函数统计当前系统空闲内存页数量以及有效进程数量。
空闲内存的统计通过遍历内核中的 freelist 完成，
而进程数量的统计则通过遍历进程表 proc[NPROC]，
并统计状态不为 UNUSED 的进程数得到。
最后，内核通过 copyout 将统计得到的结构体内容
从内核地址空间拷贝到用户地址空间，
从而完成系统调用的数据返回过程。

Q：为什么需要使用 copyout，而不能直接访问用户指针？

A：用户空间与内核空间具有不同的地址映射关系，
内核不能直接信任或访问用户提供的虚拟地址。
copyout 函数会在拷贝过程中检查地址是否合法，
并通过页表转换将数据安全地写入用户空间，
从而保证系统调用的安全性与稳定性。
