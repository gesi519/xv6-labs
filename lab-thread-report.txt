Lab Thread Report

本次 Lab 主要包括 uthread、ph 和 barrier 三个部分。
通过这次实验，我进一步理解了线程切换、并发访问、锁机制以及条件变量的使用方法。
相比只在理论上学习线程与同步机制，这次实验更强调自己动手实现，因此也遇到了不少问题。

一、uthread 部分

uthread 这一部分的主要目标是实现用户级线程库中的线程切换。
刚开始做的时候，我最困惑的问题是线程切换时到底需要保存什么、恢复什么。
因为一个线程会暂停，另一个线程会继续执行，所以必须把当前线程的重要执行现场保存下来。
否则在线程下一次被调度时，就无法从原来的位置继续执行。

一开始我对寄存器的保存范围理解得不够清楚。
尤其是不明白为什么实验中强调只需要保存 callee-saved registers。
后来我重新看了函数调用约定，并结合实验说明，逐渐明白了原因。
thread_switch 本质上和函数调用的现场保存规则有关。
调用者保存寄存器由调用者负责，而线程切换时只需要保证被调用者长期保存的寄存器不丢失。
这样线程恢复后就能够继续正常运行。
这一部分让我把“调用约定”和“线程切换”这两个原本分开理解的知识点联系了起来。

另一个比较麻烦的问题，是如何让新建线程第一次被调度时，能够从 thread_create() 传入的函数开始执行。
对于已经运行过的线程来说，只要恢复原来的寄存器和栈即可。
但对于一个从未运行过的新线程来说，它并没有“上一次执行到哪里”的状态。
因此，关键就是在创建线程时提前构造好它的上下文。
这包括为它分配独立的栈空间，并设置好第一次运行时的入口位置。
这个地方我一开始理解得比较抽象。
后来把它看成是“人为准备一个初始执行现场”，就更容易理解了。

在调试这一部分时，我也意识到汇编和 C 语言配合调试的重要性。
因为 thread_switch 在汇编里实现，所以单纯看 C 代码并不能完全理解出错原因。
有时程序没有输出，或者线程无法正常切换，并不一定是调度逻辑出错。
也有可能是寄存器保存顺序、栈指针设置或者返回地址恢复等细节出了问题。
这部分实验让我更加体会到，底层系统实验中对程序执行现场的理解非常重要。

二、ph 部分

ph 部分主要考察多线程环境下哈希表的并发安全问题。
这个部分最典型的问题就是 race condition。
单线程运行时程序完全正常。
但当线程数增加到两个时，就会出现 keys missing 的现象。
也就是说，理论上应该插入成功的 key 最终没有出现在哈希表中。

最开始看到这个结果时，我知道问题一定出在多个线程同时修改共享数据结构上。
但真正去分析时，还是花了一些时间。
后来仔细看 put() 和 insert() 的逻辑，我理解到问题的根源在于多个线程可能同时访问同一个 bucket。
它们都以为自己看到的是当前最新的链表状态。
然后它们各自执行插入操作。
由于这种操作不是原子的，因此一个线程的修改可能会覆盖另一个线程的结果。
最终就导致部分 key 丢失。
这种“每一步都看起来合理，但组合起来却出错”的现象，让我对 race condition 有了更具体的理解。

在解决这个问题时，我先采用了比较直接的方法，也就是加一个全局锁。
这样做的优点是思路很清楚。
只要有线程进入 put 或 get，就先获得锁，完成后再释放锁。
这样共享数据结构在任意时刻只会被一个线程修改。
结果也表明，missing keys 的问题确实消失了。
这说明程序的正确性得到了保证。
不过，全局锁也有明显缺点。
那就是它限制了并发性。
即使两个线程访问的是完全不同的 bucket，它们也不能同时执行，因此性能提升有限。

为了进一步通过 ph_fast 的要求，我又考虑了如何减少不必要的互斥。
实验提示中提到可以考虑每个 hash bucket 一把锁。
这个思路非常重要。
因为哈希表本身天然分成多个 bucket。
不同 bucket 之间通常是相互独立的。
如果两个线程访问的是不同 bucket，那么其实并不存在真正的数据冲突。
此时就没有必要让它们互相阻塞。
因此，把锁的粒度从“整个表”缩小到“单个 bucket”，就可以在保证正确性的同时提高并行程度。
这样做之后，我也更清楚地认识到，并发程序优化的核心不只是“加锁”，而是“在正确性和并行性之间找到平衡”。

这个部分让我收获最大的一点，是写并发程序时必须时刻思考共享状态。
单线程程序中，代码按顺序执行，比较容易根据语句顺序推断结果。
而在多线程程序中，真正的执行顺序可能千变万化。
如果不把“多个线程可能交错执行”这一点始终放在脑中，就很容易写出看似正确但实际会出错的代码。

三、barrier 部分

barrier 部分的目标是实现一个同步屏障。
它要求所有线程都到达某个点之后，才能一起继续往下执行。
这个概念在理论上并不难理解。
但真正实现时，问题比我一开始想象的复杂。
尤其是在处理多轮 barrier 的时候，更容易出现错误。

刚开始做这一部分时，我的第一反应是只要统计当前已经到达 barrier 的线程数即可。
当数量等于总线程数时，就唤醒所有线程。
这个思路在单轮 barrier 中是成立的。
但实际程序中线程会多次循环调用 barrier，也就是存在很多轮 barrier。
如果只维护一个简单的计数，而不区分当前是哪一轮，那么就会出现线程“串轮”的问题。
某个线程可能在上一轮刚被唤醒之后，很快又进入下一轮 barrier。
而其他线程此时可能还没有完全离开上一轮。
这样就会导致共享状态被提前修改，进而引发错误。

因此，这一部分最关键的地方就是 round 的概念。
必须明确地区分“当前 barrier 是第几轮”。
线程在等待时不能只看计数，还要看自己等待的是否仍然是同一轮。
只有这样，线程才不会把下一轮的状态和上一轮混在一起。
这个设计让我意识到，在并发同步问题中，除了“资源保护”之外，还有一类很重要的问题是“阶段协调”。
也就是多个线程如何在不同阶段保持一致。

另一个需要注意的点是 condition variable 的使用方式。
它通常必须和 mutex 配合使用。
而且等待时不能简单使用 if 判断。
通常需要在循环中反复检查条件是否满足。
这是因为线程被唤醒时，并不一定意味着自己真的可以继续执行。
也有可能只是被广播唤醒后重新竞争锁。
或者当前状态已经被其他线程改变。
因此，正确使用 condition variable，不只是会写 pthread_cond_wait 和 pthread_cond_broadcast 这两个函数。
更重要的是理解它背后的同步语义。

通过 barrier 这一部分，我更加深刻地体会到，并发程序中的“正确唤醒”并不像表面看起来那么简单。
很多时候，问题不在于线程有没有睡眠或唤醒。
而在于它醒来之后看到的状态是否仍然满足继续执行的条件。

四、实验总结

总体来说，这次 Lab 比较系统地训练了我对线程和同步机制的理解。
uthread 让我理解了线程切换的底层原理。
ph 让我直观地看到了 race condition 是如何产生的。
同时也理解了粗粒度加锁和细粒度加锁之间的区别。
barrier 则让我认识到条件变量和多轮同步的重要性。

通过这次实验，我最大的体会是正确性永远是并发程序中的第一位。
只有先保证程序在多线程情况下不会出错，后续的性能优化才有意义。
同时，很多并发错误并不是因为代码量大，而是因为对共享状态和线程执行顺序考虑得不够细致。
因此，以后在写涉及线程的程序时，我会更主动地分析共享资源、锁的粒度、同步条件以及不同线程之间可能出现的执行交错情况。
