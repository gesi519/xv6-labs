xv6 文件系统实验报告

一、实验目标

本次实验主要完成 xv6 文件系统部分的两个功能扩展：

1. 支持大文件。
   原始 xv6 的 inode 中有 12 个直接块地址和 1 个一级间接块地址，因此一个文件最多只能包含 12 + 256 = 268 个数据块。本实验要求增加二级间接块，使单个文件最大可达到 65803 个数据块。

2. 支持符号链接。
   实现 symlink(target, path) 系统调用，使 xv6 能够创建符号链接文件；同时修改 open，使其默认跟随符号链接，在指定 O_NOFOLLOW 时打开符号链接本身。

通过本实验，我进一步理解了 xv6 文件系统中 inode、数据块、间接块、路径查找、系统调用添加流程以及 open 对不同文件类型的处理逻辑。

二、大文件支持的实现

1. inode 地址布局修改

原始 xv6 的 inode 地址数组布局为：

  addrs[0..11]：12 个直接块
  addrs[12]：1 个一级间接块

为了在不改变磁盘 inode 大小的前提下加入二级间接块，我将直接块数量从 12 改为 11，将原本一个直接块地址的位置让给二级间接块。因此新的布局为：

  addrs[0..10]：11 个直接块
  addrs[11]：1 个一级间接块
  addrs[12]：1 个二级间接块

在 kernel/fs.h 中修改：

  #define NDIRECT 11
  #define NINDIRECT (BSIZE / sizeof(uint))
  #define NDINDIRECT (NINDIRECT * NINDIRECT)
  #define MAXFILE (NDIRECT + NINDIRECT + NDINDIRECT)

  uint addrs[NDIRECT+2];

其中 NINDIRECT = 1024 / 4 = 256，表示一个间接块可以存放 256 个 uint 类型的块号。二级间接块可以指向 256 个一级间接块，而每个一级间接块又可以指向 256 个数据块，所以二级间接块最多可以管理 256 * 256 = 65536 个数据块。

因此修改后的最大文件块数为：

  11 + 256 + 256 * 256 = 65803

同时我也在 kernel/file.h 中将 struct inode 的 addrs 数组改为：

  uint addrs[NDIRECT+2];

这样内存中的 inode 与磁盘上的 dinode 保持一致，避免文件系统读写时出现结构不匹配。

2. bmap 函数修改

bmap 的作用是将文件内部的逻辑块号 bn 映射到磁盘上的真实块号。如果目标块尚未分配，bmap 会调用 balloc 分配新的磁盘块。

修改后的 bmap 分三种情况处理：

第一种情况是直接块：

  当 bn < NDIRECT 时，直接使用 ip->addrs[bn]。如果该地址为 0，就分配一个新的数据块，并将块号写回 ip->addrs[bn]。

第二种情况是一级间接块：

  当 bn 超出直接块范围后，先执行 bn -= NDIRECT，将逻辑块号转换为一级间接区域内的偏移。如果 bn < NINDIRECT，则通过 ip->addrs[NDIRECT] 找到一级间接块。如果一级间接块不存在，则先分配一级间接块。之后读取该间接块，将其内容视为 uint 数组 a，再通过 a[bn] 找到或分配真正的数据块。

第三种情况是二级间接块：

  当 bn 进一步超出一级间接范围后，再执行 bn -= NINDIRECT，将逻辑块号转换为二级间接区域内部的偏移。对于二级间接块，需要把 bn 拆成两级下标：

    i = bn / NINDIRECT
    j = bn % NINDIRECT

  其中 i 表示二级间接块中的第几个一级间接块，j 表示该一级间接块中的第几个数据块地址。实现流程如下：

  1. 通过 ip->addrs[NDIRECT+1] 找到或分配二级间接块；
  2. 读取二级间接块，找到第 i 项，即某个一级间接块的地址；
  3. 如果该一级间接块不存在，则分配它，并将地址写入二级间接块；
  4. 释放二级间接块 buffer；
  5. 再读取刚才得到的一级间接块；
  6. 通过该一级间接块的第 j 项找到或分配真正的数据块；
  7. 返回最终的数据块号。

这里必须注意，二级间接块不能直接用 a[bn] 访问，因为二级间接块本身最多只有 256 个地址槽位，而二级间接区域的 bn 范围可达 0 到 65535。因此必须用除法和取模将其拆成两级索引。

3. itrunc 函数修改

itrunc 用于释放一个文件占用的所有数据块。原始 xv6 只释放直接块和一级间接块。加入二级间接块后，我补充了释放二级间接块的逻辑：

  1. 先释放所有直接块；
  2. 再读取一级间接块，释放其中记录的所有数据块，然后释放一级间接块本身；
  3. 对于二级间接块，先读取二级间接块；
  4. 遍历二级间接块中的每个一级间接块地址；
  5. 对每个存在的一级间接块，读取它并释放其中记录的所有数据块；
  6. 释放该一级间接块本身；
  7. 最后释放二级间接块本身，并将 ip->addrs[NDIRECT+1] 置为 0；
  8. 将 ip->size 置为 0，并调用 iupdate 更新 inode。

这样可以保证删除大文件时不会泄漏数据块和间接块。

三、符号链接的实现

1. 添加系统调用

为了实现 symlink(target, path)，我在系统调用相关文件中添加了新的系统调用入口：

  kernel/syscall.h：添加 SYS_symlink 系统调用号
  kernel/syscall.c：声明并注册 sys_symlink
  user/user.h：添加用户态函数声明 int symlink(char*, char*)
  user/usys.pl：添加 entry("symlink")

这样用户程序可以通过 symlink 系统调用进入内核。

2. 添加文件类型和 open 标志

在 kernel/stat.h 中添加新的文件类型：

  #define T_SYMLINK 4

该类型用于表示符号链接 inode。

在 kernel/fcntl.h 中添加：

  #define O_NOFOLLOW 0x800

该标志用于 open。当用户使用 O_NOFOLLOW 时，open 不跟随符号链接，而是打开符号链接文件本身。

3. 实现 sys_symlink

sys_symlink 的核心思想是：符号链接本身是一个特殊类型的文件，它的数据内容保存目标路径字符串。

实现流程如下：

  1. 使用 argstr 从用户态获取 target 和 path；
  2. 调用 begin_op 开始文件系统事务；
  3. 使用 create(path, T_SYMLINK, 0, 0) 在 path 位置创建一个 T_SYMLINK 类型的 inode；
  4. 使用 writei 将 target 字符串写入该 inode 的数据区；
  5. 释放 inode 并调用 end_op；
  6. 成功返回 0，失败返回 -1。

这里需要注意，symlink 的 target 不要求当前存在。因此 sys_symlink 不能对 target 调用 namei 来检查目标是否存在，否则会错误地拒绝指向未来文件或不存在文件的符号链接。

4. 修改 sys_open

默认情况下，open 遇到符号链接时应该跟随它，打开它指向的最终目标文件。因此我在 sys_open 中加入了处理 T_SYMLINK 的逻辑。

当 open 不带 O_NOFOLLOW 时，如果 namei(path) 得到的 inode 类型是 T_SYMLINK，就读取该符号链接 inode 中保存的目标路径，然后释放当前 inode，再用 namei(target) 重新查找目标文件。如果目标仍然是符号链接，就继续重复该过程，直到找到非符号链接文件。

为了避免符号链接循环导致死循环，例如：

  a -> b
  b -> a

我设置了最大跟随深度，例如 10 次。如果超过该深度仍然没有解析到普通文件，就返回 -1。

当 open 带有 O_NOFOLLOW 时，不进行上述跟随过程，而是直接打开符号链接 inode 本身。

本实验不要求 link、unlink 等其他系统调用跟随符号链接，因此我只修改了 open 的行为，其他系统调用仍然操作符号链接本身。

四、调试过程与问题分析

1. dinode 大小错误

在修改 NDIRECT 和 addrs 数组时，我遇到过 mkfs 报错：

  Assertion `(BSIZE % sizeof(struct dinode)) == 0' failed.

原因是 struct dinode 的大小必须能够整除 BSIZE。原始 xv6 中 dinode 大小为 64 字节，一个 1024 字节的 block 正好能放 16 个 dinode。如果只把 NDIRECT 改为 11，但仍然使用 addrs[NDIRECT+1]，那么 addrs 只有 12 项，dinode 大小会变成 60 字节，1024 不能被 60 整除，mkfs 就会失败。

最终解决方法是：

  NDIRECT = 11
  addrs[NDIRECT+2]

这样 addrs 仍然有 13 个 uint，dinode 大小保持为 64 字节。

2. 二级间接块索引错误

一开始我将二级间接块直接写成 a[bn]，这是错误的。因为二级间接块自身只有 256 个地址槽位，而二级间接区域内部的 bn 最多可以达到 65535。直接访问 a[bn] 会越界。

正确做法是：

  i = bn / NINDIRECT
  j = bn % NINDIRECT

先通过二级间接块的 a[i] 找到一级间接块，再通过一级间接块的 a[j] 找到真正的数据块。

3. 二级间接块读取层次错误

调试过程中还出现过在同一个 buffer 中同时访问 a[i] 和 a[j] 的问题。这样实际上仍然是在二级间接块里访问两个不同位置，而没有进入二级间接块指向的一级间接块。

正确做法是：读取二级间接块得到 a[i] 后，必须 brelse 该 buffer，然后用 bread 读取 a[i] 指向的一级间接块，再访问该一级间接块中的 a[j]。

4. bigfile 超时问题

在 VMware 虚拟机环境中运行 make grade 时，bigfile 测试因为运行时间超过默认限制而超时，输出中可以看到 bigfile 持续打印点号但在超时前没有输出 wrote 65803 blocks。手动运行 bigfile 后，最终可以得到：

  wrote 65803 blocks
  bigfile done; ok

这说明大文件功能逻辑正确，问题主要是本地 VMware 环境中运行 QEMU 较慢。为了在本地完整验证，我将本地 grade 脚本的 bigfile 超时时间临时调大到 400 秒，之后 make grade 可以通过。该调整仅用于本地验证，不属于文件系统实现的一部分。

五、测试结果

完成修改后，我进行了以下测试：

1. bigfile 测试

运行 bigfile 后成功输出：

  wrote 65803 blocks
  bigfile done; ok

说明二级间接块实现正确，单个文件最大大小已经从原来的 268 个块扩展到 65803 个块。

2. symlinktest 测试

运行 symlinktest，结果为：

  Start: test symlinks
  test symlinks: ok
  Start: test concurrent symlinks
  test concurrent symlinks: ok

说明 symlink 系统调用、open 默认跟随符号链接、O_NOFOLLOW 以及并发创建符号链接等功能通过测试。

3. usertests 测试

运行 usertests 或 usertests -q，文件系统相关测试如 bigfile、linktest、unlinkread、subdir 等均通过。部分测试中出现 usertrap(): unexpected scause 的输出属于 usertests 故意触发非法地址访问以测试内核保护机制，只要对应测试最后显示 OK 即为正常。

4. make grade

由于本地 VMware 环境运行 QEMU 较慢，默认 bigfile 超时时间下曾出现 timeout。将本地验证超时时间调整到 400 秒后，测试可以通过。

六、实验总结

本次实验加深了我对 xv6 文件系统设计的理解。通过实现大文件支持，我理解了 inode 中直接块、一级间接块和二级间接块之间的关系，也理解了 bmap 如何将文件逻辑块号映射到磁盘块号。二级间接块的关键在于将线性的逻辑块号拆成两级索引，从而通过“二级间接块 -> 一级间接块 -> 数据块”的结构扩展文件容量。

通过实现符号链接，我进一步理解了系统调用从用户态到内核态的添加流程，也理解了符号链接本质上是保存目标路径字符串的特殊 inode。open 对符号链接的处理体现了路径解析和 inode 类型判断之间的关系：默认情况下需要跟随符号链接，而 O_NOFOLLOW 则要求打开符号链接本身。

实验中遇到的主要问题包括 dinode 大小不匹配、二级间接块索引越界、间接块读取层次错误以及本地运行超时。这些问题帮助我更清楚地认识到文件系统实现中磁盘布局、内存结构、buffer cache、日志写入和测试环境性能之间的关系。最终，bigfile、symlinktest 和 usertests 均能够正确运行，说明本次文件系统扩展基本完成。
